# Управление складом — план командной работы

## Проект и состав
Управление складом. Учебная команда: ровно 8 человек — 5 разработчиков (D1–D5), 2 тестировщика (Q1–Q2), 1 менеджер (M). Отдельного девятого тимлида нет: D1 совмещает разработку с технической координацией. Представитель заказчика консультирует по приёмке и не входит в штат команды.
| Участник | Ответственность | Результат |
|---|---|---|
| D1 | Архитектура, API, технические решения | Контракты и интеграция |
| D2 | Бизнес-правила | Проверяемые сценарии |
| D3 | Данные и миграции | Схема, откат миграции |
| D4 | Интерфейс | Доступные формы |
| D5 | Интеграции и CI | Сборка и учебное развёртывание |
| Q1 | Сценарии и исследовательская проверка | Приёмочные протоколы |
| Q2 | Автоматизация, нагрузка, регрессия | Автотесты и измерения |
| M | Приоритеты, сроки, риски, коммуникации | Согласованный план |
## Процесс
Выбран Kanban. Причина: неодинаковые по размеру поступающие заявки; важнее ограничить очереди и время ожидания. Пополнение Ready дважды в неделю, WIP: разработка 3, review 2, test 2; блокировки остаются в лимите.
Поток: Backlog → Ready → Development → Review → Test → Accepted. Возврат из Test идёт в Development с причиной дефекта; изменение требований возвращается в Backlog на оценку. Для склада вертикальные сценарии: приёмка → размещение → резервирование → отгрузка → инвентаризация. Отрицательный остаток запрещается транзакцией, повтор сканирования защищается ключом операции.
## Матрица RACI
R выполняет, A единолично отвечает за результат, C консультирует, I информируется. В каждой строке ровно один A.
| Работа | M | D1 | D2–D5 | Q1 | Q2 |
|---|---|---|---|---|---|
| Приоритет и приёмочные критерии | A/R | C | C | C | I |
| Архитектура и API | I | A/R | R | C | C |
| Реализация и review | I | A | R | C | C |
| Приёмочные сценарии | C | C | C | A/R | R |
| Автотесты и нагрузка | I | C | R | C | A/R |
| Решение о выпуске | A | R | I | C | C |
## Коммуникации и календарь
| Когда | Формат | Участники и итог |
|---|---|---|
| Ежедневно 10:00, 15 минут | Синхронизация | Команда; препятствия, владелец и следующий шаг |
| Понедельник/четверг, 30 минут | Уточнение и пополнение | M, D1, Q1; готовые небольшие карточки |
| Раз в 2 недели, 45 минут | Демонстрация | Команда и заказчик; принятие или замечания |
| После демонстрации, 30 минут | Ретроспектива | Команда; одно улучшение с ответственным |
| Раз в неделю, 20 минут | Риски и зависимости | M и владельцы рисков; изменения плана |
Решения хранятся в задачах и ADR, обсуждение — в командном чате. Срочный дефект регистрируется с воспроизведением и ответственным; внешний канал отправки в этом учебном стенде отсутствует.
## Git и качество
Основная ветка main защищается правилами команды: короткие feature-ветки, PR, минимум один независимый reviewer, зелёный CI. Это предложенная политика, настройки защиты на GitHub данным отчётом не подтверждаются. Автор не принимает собственный PR. Конфликт: обновить ветку, согласовать смысл изменений, разрешить локально, повторить тесты, запросить review. Force-push в общую ветку запрещён.
Definition of Ready: цель, ограничения, критерии и тестовые примеры. Definition of Done: код, review, тесты, документация, миграция/откат при необходимости, принятие сценария. Пример исполнимого контракта:
```python
def reserve(stock, quantity):
    if quantity <= 0 or quantity > stock:
        raise ValueError("Недостаточный остаток или неверное количество")
    return stock - quantity


assert reserve(10, 3) == 7
```
Это иллюстрация правила; реальная конкурентная запись требует транзакции в БД.
## Риски и изменения
| Риск | Признак | Действие | Владелец |
|---|---|---|---|
| Очередь проверки | Review старше 1 рабочего дня | Помочь review до новой разработки | D1 |
| Неясное требование | Противоречивые критерии | Пример с заказчиком до реализации | M |
| Сбой интеграции | Повторные ошибки контракта | Mock и контрактный тест | D5 |
| Потеря данных | Неудачное восстановление | Остановить выпуск, исправить процедуру | D3 |
| Недоступность специалиста | Единственный владелец модуля | Парная работа и инструкция | D1 |
Спор о решении: записать варианты и критерии, ограничить обсуждение 30 минутами, провести небольшой эксперимент; технический выбор фиксирует D1, приоритет — M. Изменение объёма оценивают разработчики и QA, M согласует обмен приоритетами; сроки не обещаются без переоценки.
## План на 6 недель и контроль
1–2: модели, контракты и первый сквозной сценарий. 3–4: основной процесс и отрицательные сценарии. 5–6: интеграция, восстановление, приёмка. Это план, не отчёт о проведённых встречах. Раз в неделю измерять cycle time, возраст открытых задач, число возвратов и дефекты после выпуска; сравнивать одинаковые типы работ. Превышение возраста 3 рабочих дня требует разбора препятствия, а не обвинения исполнителя.
